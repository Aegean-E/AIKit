# AIKit Principles: Single Source of Truth (Tier 2)

> This is the **only** hand-edited copy of AIKit's engineering principles. Every always-injected Tier 1 file (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.cursorrules`, `.github/copilot-instructions.md`, `.agents/rules/principles.md`) is generated from it by `python scripts/sync_principles.py`; edit here, never there.
>
> **Do not load this file whole** unless the user asks. It is Tier 2 knowledge (PRINCIPLE-001 R3): on a contract change, a failure or an ambiguity, read only the matching `### PRINCIPLE-NNN:` section.
>
> **Reading the rules:** MUST, MUST NOT and MAY carry their RFC 2119 meaning. A rule tagged *[Agent]* binds every AI agent in every session; *[Maintainer]* binds whoever edits `GUIDELINES.md`, `scripts/sync_principles.py` or `.agents/rules/domain.md`.

Principles follow the 5-step execution lifecycle (PRINCIPLE-002): Meta-Governance & Grounding, Pre-Flight Orientation & Planning, Architecture & Lean Implementation, Operational Verification & Resilience, Living Sync & Delivery. Each carries a **Problem** (why it exists), a **Concept**, an **Invariant** (the capsule injected into Tier 1, so exact mechanisms only), and numbered **Rules**.

## 🏛️ Phase 1: Meta-Governance & Attentional Grounding

### PRINCIPLE-000: Meta-Principle Integrity & Mutual Alignment (Code Quality Primacy)
- **Problem**: When principles operate without systemic meta-governance, individual rules risk being selectively adhered to or bypassed; uncoordinated updates introduce contradictions between principles; rule changes lack cross-impact verification; dogmatic compliance compromises code quality; and agents exploit loopholes to technically pass gates while violating engineering intent.
- **Concept**: Five meta-rules that every model applies the same way: every rule binds unless a rule states the exception; a conflict has one definition and one resolution order; a rule change is checked against every rule that cites it; passing a gate without delivering what it checks is a violation; and every rule names a condition that can be decided true or false.
- **Invariant**: Every rule binds; conflicts follow R6 order; rule edits re-check every citing principle; gaming a gate is a violation; quality doubts go to the user.
- **Rules**:
  1. **Universal Adherence Invariant** *[Agent + Maintainer]*: Every rule in `GUIDELINES.md` binds every task its text covers. The agent MUST NOT skip or weaken a rule unless `GUIDELINES.md` states the exception explicitly, in that rule or in a rule that names it. An exception exists only where that text names its condition, such as the informed override of PRINCIPLE-002 R5 or a user's explicit approval a rule asks for; an agent's own judgment that a rule does not fit is never one (R4).
  2. **Mutual Alignment & Non-Contradiction** *[Agent + Maintainer]*: Two rules *conflict* when, at the same step, obeying one requires an action the other forbids, or forbids an action the other requires. A change to `GUIDELINES.md` MUST NOT introduce a conflict. An agent that meets a conflict MUST resolve it by R6, follow the winning rule, and report the conflict to the user in one line naming both rules as `PRINCIPLE-NNN RN`.
  3. **Cross-Principle Impact Verification Gate** *[Agent + Maintainer]*: A principle is *changed* when its `### PRINCIPLE-NNN:` section in `GUIDELINES.md` differs from the last commit, ignoring trailing whitespace. Before committing, the agent MUST run `git grep -n -w -e PRINCIPLE-NNN` for each changed principle and update or verify every hit except those in `knowledge/decisions.md` (past ADRs are never edited, PRINCIPLE-016 R3) and `.agents/task_ledger.json` (bookkeeping) (PRINCIPLE-003 R2), and MUST add an ADR (PRINCIPLE-004 R4) containing a line starting `Cross-principle check:` that names every principle `python scripts/sync_principles.py --citing PRINCIPLE-NNN` prints for each changed principle, each followed by `no conflict` or by the conflict and how the change resolves it. `python scripts/sync_principles.py --check` fails while a changed principle has no ADR added since the last commit naming that whole set. The ADR's ID is read from the register, never recalled: `python scripts/update_knowledge_base.py` rejects a duplicate or skipped ID.
  4. **Code Quality & Craftsmanship Primacy** *[Agent]*: When the agent judges that obeying a rule literally would make the code or its tests worse (duplicated logic, a weaker or slower test, a workaround around a gate), it MUST NOT deviate from the rule on its own and MUST NOT write the worse code without saying so: it stops and asks the user once (PRINCIPLE-003 R6), naming the rule, the code affected and a proposed rule change. Code quality never licenses skipping a rule.
  5. **Anti-Malicious Compliance & Intent Fidelity** *[Agent]*: These are violations even when every gate passes: an assertion that cannot fail; weakening a test (as PRINCIPLE-014 R2 defines it) without the user approval and ADR that rule requires, or loosening a threshold, allowlist entry or budget to make a check pass without an ADR that states why; code that behaves differently when it detects a test or a check; a stub or constant written to satisfy a test while the behaviour the test describes is missing; an `except` block that neither re-raises, returns or exits with an error, nor writes a warning, unless it only cleans up after an error that is already raised or reported; and any change after which a check passes while the behaviour the check describes is still false.
  6. **Deterministic Resolution Hierarchy** *[Agent + Maintainer]*: A conflict (R2) between rules of two principles is decided by this order, the earlier tier winning: (1) PRINCIPLE-019, PRINCIPLE-013; (2) PRINCIPLE-003, PRINCIPLE-014; (3) PRINCIPLE-000, PRINCIPLE-009; (4) PRINCIPLE-001, PRINCIPLE-012. When both principles are in one tier, or either is in none, the rule that cites the other rule wins; when neither cites the other or each cites the other, the agent MUST stop and ask the user (PRINCIPLE-003 R6). A rule cites another when its text contains that rule's `PRINCIPLE-NNN RN` or, for the whole principle, its `PRINCIPLE-NNN`. A conflict between a capsule and `GUIDELINES.md`, or between a user instruction and a principle, is decided by PRINCIPLE-001 R1, not by this order.
  7. **Mechanical Falsifiability & Anti-Vagueness** *[Agent + Maintainer]*: Every rule added or changed MUST state a condition that a command, a test, or a reading of the diff, the commit or the files decides as true or false, and MUST name who it binds (*[Agent]*, *[Maintainer]* or *[Agent + Maintainer]*). It MUST NOT use these words: `e.g.`, `etc.`, `relevant`, `proactively`, `essential`, `excessive`, `concise`, `dense`, `appropriate`, `as needed`, `~`, `should`, `where possible`, `mentally`, `$\rightarrow$`, `zero-friction`, `instantly`.

### PRINCIPLE-001: Progressive Rule Disclosure & Governance Frugality (Zero Instruction Bloat)
- **Problem**: Rules that are always loaded consume context on every turn and compete with the task for the model's attention, so long rule files lower accuracy instead of raising it. Short but vague rules fail differently: each model resolves the vagueness its own way, and agents stop behaving alike.
- **Concept**: Governance is split into two tiers. Tier 1 is a generated set of one-line capsules that every agent loads automatically. Tier 2 is the full rule text in `GUIDELINES.md`, read one section at a time when a named trigger fires. Every rule names who it binds and what to do; rules about files are checked by `scripts/sync_principles.py` and the test suite, and rules about agent conduct are checked by the report that R8 requires.
- **Invariant**: Pre-Flight checklist before the first Track C edit; Post-Flight checklist before any Track B or C commit; report only failed items (R8).
- **Rules**:
  1. **Two-Tier Progressive Disclosure** *[Agent + Maintainer]*:
     - *Tier 1* is exactly the files listed in `TIER1_TARGETS` in `scripts/sync_principles.py`: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.cursorrules`, `.github/copilot-instructions.md` and `.agents/rules/principles.md`. Each contains only a generated header, one capsule line per principle, and the optional Tier 1B block. Tier 1 files MUST NOT be edited by hand; `scripts/sync_principles.py` regenerates them and refuses to overwrite any file it did not generate.
     - *Tier 2* is `GUIDELINES.md` (all rule text) plus `knowledge/` (project architecture, schemas and decisions).
     - *Precedence*: Tier 1 capsules bind every agent. A capsule summarises its `GUIDELINES.md` section; when the two disagree, the agent MUST follow `GUIDELINES.md` and MUST report the mismatch to the user in its next message, in one line naming the principle ID. An explicit user instruction overrides exactly two things in this principle: the R3 obligation to read a section, and the R3 ban on loading `GUIDELINES.md` in full. It does not override another principle: a conflict between a user instruction and another principle is decided by that principle's own rules, including PRINCIPLE-002 R5.
     - Any file that a tool loads automatically by convention is Tier 1 whatever its intended role, so it MUST be a generated target. When a tool starts auto-loading a new file, that file MUST be added to `TIER1_TARGETS`.
  2. **Self-Sufficient Invariant Capsules** *[Maintainer]*: A capsule is the `- **Invariant**:` line of a principle; it is copied verbatim into every Tier 1 file. It MUST name every command, script, file path, numeric threshold and named gate that the principle's *[Agent]* rules require an agent to run or respect. It MUST NOT contain rationale, examples, or adjectives that name no mechanism. Deletion test: a phrase whose removal loses no command, path, number or named rule MUST be removed.
  3. **Tier 2 Retrieval Triggers** *[Agent]*: When a trigger below occurs, the agent MUST read the `GUIDELINES.md` section of every involved principle before any further file edit or commit, and before running any command other than those needed to compute the involved principles and read their sections. A principle is *involved* when a backtick-quoted name in its capsule (a file, path, script or command) occurs verbatim in the paths the agent will change, the commands it will run, or the failing output, or when that text contains the principle's ID; when nothing matches, the involved principle is PRINCIPLE-003. `python scripts/sync_principles.py --involved <text>` computes this list and is authoritative. The triggers are:
     - *Contract-change trigger*: adding, removing or renaming a source file, a public function (a module-level name not starting with `_`) or its parameters, a CLI flag, a file format, or a data schema.
     - *Failure trigger*: a failing test, a gate script exiting non-zero, a build error, or an unhandled exception. Pass the failing output to `--involved`; any principle ID it contains is involved.
     - *Ambiguity trigger*: the request or the capsules allow two or more implementations that differ in return values, printed output, files written, exit codes, CLI flags or persisted data. If the involved sections do not settle the choice, the agent MUST ask the user (PRINCIPLE-003 R6) and MUST NOT pick one silently.
     The agent MAY read a section at any other time. The agent MUST NOT load `GUIDELINES.md` in full unless the user explicitly asks; reading every principle section one after another counts as loading it in full.
  4. **Universal vs. Domain Rule Partitioning** *[Maintainer]*:
     - *Tier 1A* is the universal principles in `GUIDELINES.md`. Their size is limited by R6: with no domain file present, every Tier 1 file MUST still fit a full Tier 1B block.
     - *Tier 1B* is project-specific rules in `.agents/rules/domain.md`, at most 1,200 characters (300 estimated tokens), started from `.agents/rules/domain.md.template` and injected below Tier 1A in every Tier 1 file.
     - *Tier 2* for a project is its architecture, schemas and API specifications in `knowledge/`.
  5. **Deterministic Grep Anchor Contract** *[Agent + Maintainer]*: Every principle MUST have exactly one heading of the form `### PRINCIPLE-NNN: Title` in `GUIDELINES.md`, where NNN is three digits; `NNN` is the only placeholder used for an ID. IDs MUST NOT be renumbered or reused. To read a principle, search for the literal text `### PRINCIPLE-NNN:` with any text-search tool and read from that line up to the next line that starts with `### `, `## ` or `---`. Agents MUST NOT rely on remembered line numbers.
  6. **Strict Injected Context Budget & Automated Gate** *[Maintainer]*: Estimated tokens are the character count divided by 4, rounded down. Each Tier 1 file MUST be at most 1,600 estimated tokens including its Tier 1B block, and with no domain file present MUST still fit a 1,200-character Tier 1B block within 1,600. `python scripts/sync_principles.py` and its `--check` mode exit 1 on either breach, and the breach blocks the commit through gate (2) of PRINCIPLE-018 R3. The warning at 1,440 estimated tokens (90%) is advisory and is evaluated only after both blocking checks.
  7. **Single Source & No Decoration** *[Maintainer]*: Rule text exists only in `GUIDELINES.md`. Other files MAY cite a principle by ID and MAY summarise it in one sentence or one table row, as the `README.md` principle table does, but MUST NOT copy rule text. Generated files MUST NOT use formatting that names no mechanism (bold, emoji, repeated headings).
  8. **Terse Checklist Execution** *[Agent]*: The checklists are the *Pre-Flight Checklist* and *Post-Flight Checklist* sections of `GUIDELINES.md`; reading them is allowed under R3. On a Track C task (PRINCIPLE-002 R3) the agent MUST evaluate the Pre-Flight checklist before its first file edit of the task. On Track B and Track C tasks it MUST evaluate the Post-Flight checklist before committing. Track A tasks evaluate neither. The agent MUST NOT paste either checklist into the conversation; it reports only failed or skipped items, one line each naming the principle ID, and when nothing failed it reports `checklists passed`. An item that does not apply to the task counts as passed and is not reported; *skipped* means the item applies but was not done.
  9. **Zero Context Bloat on Expansion** *[Maintainer]*: A change that raises any Tier 1 file's estimate MUST still pass both R6 checks; when it does not, the maintainer MUST shorten existing capsules by R2's deletion test until it does. `TARGET_TOKEN_BUDGET` and `MAX_DOMAIN_CHARS` MUST NOT be raised without the user's explicit approval and a new ADR in `knowledge/decisions.md`.

### PRINCIPLE-002: Lifecycle-Aligned Instruction Ordering & Attentional Priming (Cognitive Flow Invariant)
- **Problem**: Agents that skip verification, edit tests to make failures disappear, or give in to "just push it" ship broken work; agents that run a full five-phase ceremony for a one-word typo waste the user's time. When the track and the phase gates are left to judgement, each model draws the line in a different place.
- **Concept**: Every task moves through five phases in a fixed order: Grounding -> Planning -> Implementation -> Verification -> Delivery. Delivery is locked until verification passes on the exact tree being delivered. Which phases a task needs depends on its track, and the track is computed from the files the task changes, not judged.
- **Invariant**: Track via `disruption_recovery.py --track` (A none, B docs/comments but not rule files, C rest); urgency alone never skips P018 gates (R5).
- **Rules**:
  1. **Monotonic Execution Gating (Lock-Step Integrity)** *[Agent]*: The phases are: Phase 1 Grounding (the Tier 1 capsules, plus `python scripts/disruption_recovery.py --resume` on a cold start per PRINCIPLE-004 R2; a cold start is the first turn of a session and the first turn after conversation compaction); Phase 2 Planning (the PRINCIPLE-007 impact checkpoint and the Pre-Flight checklist, PRINCIPLE-001 R8); Phase 3 Implementation; Phase 4 Verification (every command in gates (1) and (2) of PRINCIPLE-018 R3); Phase 5 Delivery (the Post-Flight checklist, commit, push). The agent MUST NOT start a phase until every earlier phase its track requires has completed. The agent MUST NOT commit or push unless every Phase 4 command passed on the exact tree being committed; any file edit after Phase 4 passed requires running Phase 4 again. Writes to `.agents/task_ledger.json` made by `scripts/disruption_recovery.py` are bookkeeping: they never require re-running Phase 4 and never change the track.
  2. **Remediation Recoil Protocol (Phase 4 Failure)** *[Agent]*: When any Phase 4 command fails, the agent MUST stop forward progress. It MUST return to Phase 2 when the fix adds, removes or renames a public contract (the contract-change trigger of PRINCIPLE-001 R3) or when `--track` now reports a higher track than the task was running on, and to Phase 3 otherwise. After the fix it MUST run every Phase 4 command again, not only the one that failed. Changes to test assertions are governed by PRINCIPLE-014 R2.
  3. **Adaptive Lifecycle Pathing & Automatic Escalation** *[Agent]*: The track is the output of `python scripts/disruption_recovery.py --track`, computed from every changed, staged and untracked file versus `HEAD`, ignoring the bookkeeping file `.agents/task_ledger.json`:
     - *Track A*: no file changes. Phase 1, then the answer.
     - *Track B*: every changed file is either documentation (`.md`, `.txt` or `.rst`, except `GUIDELINES.md`, the Tier 1 files and `domain.md`) or a Python file whose syntax tree is unchanged apart from docstrings, so only comments, docstrings or formatting changed. Phases 1, 3, 4 and 5; Phase 2 is skipped.
     - *Track C*: every other change, including code, tests, configuration, schemas, added or deleted Python files, and rule text. All five phases.
     Before its first edit the agent MUST predict the track by applying these definitions to the files it plans to change. Before committing it MUST run `--track`; when the result is higher than predicted, it MUST complete the phases it skipped (Phase 2 for Track C) before committing. Phase 4 is the same full gate set for Track B and Track C.
  4. **Compaction Phase Resumption** *[Agent]*: On a Track C task the agent MUST record a checkpoint on entering each phase; on a Track B task, one checkpoint on entering Phase 3. The command is `python scripts/disruption_recovery.py --checkpoint <task_id> --phase-num <1-5> --desc <text>`, where `<task_id>` is one kebab-case name used for the whole task. After Phase 5 the agent MUST run `python scripts/disruption_recovery.py --complete <task_id>`. After conversation compaction or a cold restart it MUST run `python scripts/disruption_recovery.py --resume` and continue at the phase printed on its `Recommended Resumption Phase` line. A recorded phase means the phase was entered, not finished, so the agent resumes inside it. It MUST NOT repeat a completed phase, except that Phase 4 runs again whenever the tree changed after it last passed.
  5. **Immunity to Late-Stage User Priming** *[Agent]*: Urgent wording such as "commit now", "push immediately" or "skip the tests" does not change R1; the agent runs the remaining Phase 4 commands and then delivers. If one of them fails, R2 applies and the agent reports the failure before doing anything else. The agent MAY commit and push before Phase 4 passes only when the user, after the agent has named each unrun or failing gate, explicitly instructs it to deliver anyway; that commit message MUST end with the line `Unverified: <the gates named>`. Force-pushing remains governed by PRINCIPLE-018 R4.
  6. **Primacy-Weighted Anchoring** *[Maintainer]*: Principles appear in `GUIDELINES.md` and in every Tier 1 file in ascending phase order and, within a phase, ascending ID order, so grounding rules come first and delivery rules last. Checklist items appear in ascending principle-ID order. Tier 1 files inherit this order because `scripts/sync_principles.py` renders them in `GUIDELINES.md` order.
  7. **Continuous Sequence Audit** *[Maintainer]*: `parse_principles()` in `scripts/sync_principles.py` MUST reject a principle whose phase is lower than the phase of the principle before it, and a principle list whose last phase is not 5. `sync_principles.py`, its `--check` mode and the test suite run this check, so a phase inversion blocks the commit.

### PRINCIPLE-003: Empirical Grounding & Anti-Hallucination Invariant (Verify-Before-Execution)
- **Problem**: Models that write from memory instead of from the repository invent imports, call functions with signatures that no longer exist, edit text that has moved, leave renamed symbols orphaned, and assume a shell that is not there. When "ambiguity" is not defined, one model guesses silently while another stops to ask.
- **Concept**: Every symbol, dependency and platform assumption is checked against the repository or the running environment before it is used. Ambiguity is split by who faces it: the running program handles uncertain input with a documented default, and the agent asks the user about uncertain intent.
- **Invariant**: Read-before-write slice freshness; `git grep -w -e` call-site check; deps only if declared; platform parity; ask on intent ambiguity; strict AST syntax gate.
- **Rules**:
  1. **Read-Before-Write & Target Slice Freshness** *[Agent]*: Before replacing or deleting existing text in a file, including overwriting the whole file, the agent MUST have read that exact text, and the file MUST NOT have been written since that read; if it has, the agent reads the text again. Before calling a function, instantiating a class or passing a command-line flag defined in this repository, the agent MUST read its definition: from the source, from `knowledge/codebase_map.md` when `python scripts/update_knowledge_base.py --check` passes (the map then matches the code exactly), or, for a flag, from the script's `--help` output. Consulting the map to navigate (PRINCIPLE-004 R3) does not satisfy this rule unless that check passes.
  2. **Call-Site & Reference Completeness** *[Agent]*: Before renaming or deleting a function, class, constant, command-line flag, configuration key, file or schema field, or changing a function's parameters, the agent MUST run `git grep -n -w -e <name>` (the `-e` is required: without it a name that starts with `-`, such as a flag, is read as a git option and the search fails), or an equivalent whole-word search over every tracked file, including tests and documentation. In the same change it MUST update every hit, or state in the commit message why a hit stays. Hits in `knowledge/decisions.md` always stay unchanged, because past ADRs are append-only (PRINCIPLE-016 R3). After deleting code it MUST run `python scripts/check_reachability.py` (PRINCIPLE-014 R7).
  3. **Manifest-Backed Dependency Grounding** *[Agent]*: A *dependency* is any import outside the language's standard library and any external program the code runs. The agent MUST NOT add a dependency unless it is already declared in the project's manifest (`pyproject.toml`, `requirements.txt`, `package.json`, `Cargo.toml` or `go.mod`) or, in a repository with no manifest, in the `Runtime Prerequisites` line of `README.md`. Declaring a new dependency requires the user's explicit approval; the agent MUST NOT add it to the manifest or to `README.md` on its own. Programs that ship with a supported operating system, such as `taskkill` on Windows, are platform and fall under R4. AIKit has no manifest; its declared dependencies are Python 3.10+ and `git`.
  4. **Platform & Runtime Parity** *[Agent]*: Code written for the repository MUST build paths with `pathlib.Path` and never hardcode `/` or `\` as a separator; MUST start Python subprocesses with `sys.executable`; MUST pass subprocess arguments as a list and MUST NOT use `shell=True` or `os.system`; and MUST guard operating-system-specific calls with `sys.platform`, as `fsync_dir()` and `terminate_process_tree()` do. Code MUST run on the oldest runtime the repository declares (Python 3.10 for AIKit): it MUST NOT use syntax or standard-library APIs introduced after that version, even when the agent's own interpreter is newer. Commands in documentation use `python`. Commands the agent runs itself use the launcher and shell its environment reports, not ones copied from documentation.
  5. **Bi-Directional Contract Parity** *[Agent]*: When changing a data schema, a file format, command output that another program parses, a function signature, or what a function returns or raises, the agent MUST find every producer and every consumer with the R2 search and update or verify each one in the same commit, together with the matching `knowledge/` document (PRINCIPLE-016 R2).
  6. **Dual-Track Ambiguity Protocol & Epistemic Triad** *[Agent]*:
     - *Epistemic Triad Gate*: before the first file edit of a task, the agent MUST have checked (1) Symbol Reality: R1 for every symbol it will call or change; (2) Dependency Reality: R3 for every import and program it will add; (3) Platform Reality: R4 for the code it will write.
     - The deciding question for any ambiguity is who faces it: the running program, or the agent while deciding what to build.
     - *Runtime ambiguity* (the running program faces it): when input the program needs is absent, unreadable or malformed at run time (a file it expects, a required environment variable or argument, a record it cannot parse, a measurement that fails), the code MUST either use a default documented in the code or fail with the remediation triad of PRINCIPLE-011 R6, and MUST print a warning whenever it falls back to the default. An optional argument the user simply did not give is not missing input and needs no warning. Catching a broad exception and continuing silently (`except Exception: pass`) is an undocumented guess and MUST NOT be used.
     - *Intent ambiguity* (the agent faces it): when the request or the rules allow implementations whose observable behaviour differs (the ambiguity trigger of PRINCIPLE-001 R3) and the involved sections do not settle it, the agent MUST ask the user in one message, listing the options numbered, each with its observable difference. Until the user answers it MAY continue work that does not depend on the answer, and it MUST NOT take a destructive action: deleting or overwriting files or data the task did not create, rewriting git history, force-pushing, or removing a schema field.
  7. **Strict AST & Syntax Gating** *[Agent + Maintainer]*: After editing any `.py` file the agent MUST run `python scripts/update_knowledge_base.py` before Phase 4. It parses every Python file in the repository with the grammar of the oldest supported Python (`MIN_PYTHON`) and, on any syntax error, including syntax only newer versions accept, exits 1 and names the file and line without a traceback. For other languages, the project's compiler or type checker in check mode fills this role and MUST be named in that project's `README.md`.

### PRINCIPLE-004: Attentional Drift Prevention & Compaction Resilience (Context Anchor Protocol)
- **Problem**: In long sessions the agent forgets constraints, reprints plans that bloat the conversation, floods context with unbounded output, and loses everything that lived only in chat when the conversation is compacted; afterwards it asks the user questions that were already answered. When the rules do not say where a plan or a decision is written, each model keeps it somewhere different, or nowhere.
- **Concept**: Anything the agent will need after compaction is written to a named file at a named moment, and is read back with a named command. Chat holds progress, not state.
- **Invariant**: Plan = latest `[1/` Phase 2 `--desc` in `task_ledger.json`; cold start `--resume`; never re-ask recorded answers; ADR before commit; reads/output <=100 lines.
- **Rules**:
  1. **Externalized Working Memory & Living Plan SSOT** *[Agent]*: This rule applies to Track C tasks. The plan is the `--desc` text of the task's latest `--phase-num 2` checkpoint (PRINCIPLE-002 R4) whose `--desc` starts with `[1/`; it lists every milestone as `[N/M] <milestone>` (PRINCIPLE-008). When the plan changes, the agent MUST record a new such checkpoint with the full revised plan. Any other Phase 2 checkpoint (a user's answer, a note) MUST NOT start with `[1/`. When the user answers a question about the task, the agent MUST record the answer as the `--desc` of a checkpoint in the current phase before its next file edit. The agent MUST NOT reprint a recorded plan unless the user asks to see it; it names milestones by their `[N/M]` instead. `scripts/disruption_recovery.py` keeps the ledger at most 20 checkpoints and always keeps the active task's plan checkpoint.
  2. **Compaction Resumption & Anti-Repetition Invariant** *[Agent]*: On a cold start (as defined in PRINCIPLE-002 R1) the agent MUST run `python scripts/disruption_recovery.py --resume` before any other action. It prints every `--audit` finding, so it also satisfies PRINCIPLE-002 R1 and PRINCIPLE-006 R2. Then: when it prints `BLOCKED`, the agent resolves the conflicts first; when it prints an interrupted task, the agent continues that task at the `Recommended Resumption Phase` with the printed plan (PRINCIPLE-002 R4); when it lists modified or untracked files with no interrupted task, the agent MUST NOT overwrite or discard them and MUST tell the user they exist before starting work. Before asking the user a question (PRINCIPLE-003 R6), the agent MUST check the `--resume` output and search `knowledge/decisions.md` for the subject; when a record answers the question, the agent MUST NOT ask it, and when records disagree the newest wins. A user who changes a recorded decision is followed; the agent records the change as a new checkpoint or, for an architectural decision, a new ADR that supersedes the old one (PRINCIPLE-016 R3).
  3. **AST-First & Slice-Capped Retrieval** *[Agent]*: To find code, the agent MUST search first (`knowledge/codebase_map.md` when it is fresh per PRINCIPLE-003 R1, or a whole-word text search) and open files only at the lines found; line numbers the agent already got from a search or read in this task count as found. A *read* is any tool call or command that prints file contents (a file-read tool, `cat`, `type`, `Get-Content`, `sed -n`, `head`, `tail`). One read MUST NOT print more than 100 lines of a file, of any type; a larger region, including a whole file that PRINCIPLE-003 R1 requires reading before an overwrite, is read in consecutive slices of at most 100 lines. The user's explicit request to read more overrides this cap.
  4. **Two-Tier Memory Partitioning & Immediate ADR Persistence** *[Agent]*: In-flight task state (plan, phase, answers that matter only to the current task) goes in `.agents/task_ledger.json` through `scripts/disruption_recovery.py --checkpoint`. An *architectural decision* is one that: changes a public contract (a command-line flag, exit code, file format, data schema, command output another program parses, or the signature of a function called from another module); adds or removes a dependency (PRINCIPLE-003 R3); changes a principle, rule or numeric limit in `GUIDELINES.md`; or is a user instruction the user says applies to future tasks or to the whole project. Each one MUST be appended to `knowledge/decisions.md` as an ADR before the next commit, and before the turn ends when no commit follows. A schema's fields are written only to `knowledge/data_models.md` (PRINCIPLE-016 R5); the ADR records the decision and names that file. Past ADRs are never edited (PRINCIPLE-016 R3).
  5. **Terse Tool Invocation & Bounded Messages** *[Agent]*: The output of one command the agent runs MUST NOT put more than 100 lines into the conversation; the agent limits it with a summary form (`git status --short`, `git log -n 1 --oneline`, `git diff --stat`) or a line limit (`| head -n 100`, `| tail -n 20`). Diffs and searches have the tighter limits of PRINCIPLE-012 R3. Every message the agent writes before the final message of its turn MUST be at most 15 lines, code blocks included; the final message is not limited by this rule. Checklist timing is set by PRINCIPLE-001 R8, not by this rule.

### PRINCIPLE-005: AI Cold-Start Readiness & Living Documentation (README Sync)
- **Problem**: New AI sessions and developers starting fresh ("cold start") lose context if documentation is stale, fragmented, or implicit. Furthermore, rotting quickstart commands waste developer and agent turns, unmonitored directory trees drift out of date as files are added or renamed, unbounded README files exhaust the active context window on turn 1, and indiscriminate sync rules cause documentation churn on internal refactors.
- **Concept**: `README.md` is the cold-start entry point, built from labelled items a program can check: what to install, the one test command, and a tree of what exists. It changes in the same commit as anything a user can observe, and only then; everything else is documented in `knowledge/`.
- **Invariant**: README <=20k chars: prerequisites, test command, tree; user-visible changes update it same commit; `update_knowledge_base.py --check` gates it.
- **Rules**:
  1. **Self-Describing Repository, 30-Second Orientation & Token Ceiling** *[Agent + Maintainer]*: `README.md` MUST contain a heading that includes `Cold-Start Quick Reference`; inside the section it opens (up to the next heading of the same or a higher level), a line starting `- **Runtime Prerequisites**:` that names every runtime and external program the project needs with its minimum version, and the label `**Canonical Regression Shield Gate**:` followed by a fenced block holding the one command that runs the whole test suite; and a heading that includes `What's Inside`, followed by the directory tree of R5. No `<FILL:` placeholder from the R6 template may remain. `README.md` MUST NOT exceed 20,000 characters; material beyond that limit goes to `knowledge/` (R4). `python scripts/update_knowledge_base.py --check` checks every requirement of this rule.
  2. **Material Surface Sync Contract** *[Agent]*: The agent MUST update `README.md` in the same commit as a change that: adds, removes or renames a tracked top-level file or directory, or a file in a directory the tree shows with children (R5); adds, removes or renames a script, command-line flag, exit code or environment variable a user can use; changes what a command documented in `README.md` checks, writes or prints, or a condition under which it exits non-zero, in which case the same commit also updates that script's `--help`; or changes the runtime prerequisites, the setup steps or the test command. README's principle table needs no hand edit: `python scripts/sync_principles.py` regenerates it (R4). For any other change the agent MUST NOT edit `README.md`; its documentation goes to `knowledge/` per PRINCIPLE-016 R2.
  3. **Executable Command Parity** *[Agent + Maintainer]*: Every `python scripts/<name>.py` command in `README.md` MUST name an existing script and only flags that script declares, and every `python -m unittest tests.<module>` command MUST name an existing module; the R1 check verifies both. Before adding or changing any other command in `README.md` (a `git`, copy or package-manager command), the agent MUST run it, in a temporary directory when it copies, moves or deletes files, and it MUST exit 0. A value the reader supplies is written `<name>`.
  4. **Documentation Partitioning (The SSOT Triad)** *[Agent]*: Each fact has one home, chosen by who uses it:
     - a command a user runs or a file a user opens: `README.md`;
     - a rule an agent obeys: `GUIDELINES.md`, the only hand-edited rule file; every Tier 1 file, `AGENTS.md` included, is generated from it;
     - how the code works and why: the `knowledge/` file PRINCIPLE-016 assigns (schemas in `data_models.md`, decisions in `decisions.md`).
     `README.md` lists the principles only in the table `python scripts/sync_principles.py` generates between its `<!-- principles:begin` and `<!-- principles:end -->` markers (each principle's title and capsule, PRINCIPLE-017 R4); `--check` fails while that table is stale. `README.md` MUST NOT restate a principle's rules anywhere.
  5. **Whole-Tree Drift Shield & Script Parity** *[Agent + Maintainer]*: The tree is the first ```` ```text ```` block after the `What's Inside` heading; its first line is the repository root. Every path in the tree MUST exist; the tree MUST list every tracked top-level file and directory; and a directory shown with at least one child MUST list all of its tracked children, while a directory shown with none is collapsed and exempt. The R1 check compares the tree with `git ls-files`.
  6. **Universal Polyglot Adopter Blueprint** *[Agent]*: A project adopting AIKit, in any language, MUST start its Quick Reference and tree from `.agents/rules/readme_quickref.md.template` and MUST NOT copy AIKit's own Quick Reference, which names AIKit's test modules. In a project not written in Python, `- **Runtime Prerequisites**:` names that stack's toolchains with minimum versions, `**Canonical Regression Shield Gate**:` holds that stack's own test command, and the Quick Reference lists the build and run commands the project has. The R1 check verifies only `python scripts/...` and `python -m unittest` commands, so every other command falls under the run-before-documenting duty of R3.

### PRINCIPLE-006: Incremental Progress Checkpointing & Disruption Recovery (Zero-Progress-Loss Workflow)
- **Problem**: When electricity cuts out or hardware crashes during a multi-file task, uncommitted work is lost, files can be half-edited, temporary buffers are left behind, and the next agent cannot tell what was interrupted. When the rules do not say when to commit or what makes a task abandoned, one model commits after every file and another only at the end, and an interrupted task can vanish when the next one starts.
- **Concept**: Work survives a crash because each plan milestone is committed as soon as it passes the gates, work that does not pass yet is described in the ledger instead of committed, and every task ends with `--complete` or `--reset`.
- **Invariant**: Commit each `[milestone N/M]` once Phase 4 passes; failing work stays uncommitted, described by `--checkpoint`; `--complete` or `--reset` before switching tasks; `--clean` stale `.tmp_*`.
- **Rules**:
  1. **Micro-Milestone Atomicity & Conventional Micro-Commits** *[Agent]*: On a Track C task whose plan (PRINCIPLE-004 R1) has M milestones with 2 <= M <= 6, the agent MUST commit once per milestone, as soon as that milestone's Phase 4 commands pass (PRINCIPLE-002 R1), with the subject `type(scope): [milestone N/M] <description>`, and MUST NOT start milestone N+1 while milestone N is finished but uncommitted. A plan with one milestone is committed once, without a tag. `python scripts/disruption_recovery.py --validate-commit` rejects a tag that does not open the description or lies outside 1 <= N <= M, 2 <= M <= 6.
  2. **Pre-flight Disruption Audit on Cold Start** *[Agent]*: The cold-start audit is PRINCIPLE-004 R2: `python scripts/disruption_recovery.py --resume` before any other action, and every modified, untracked or temporary file it lists is reported to the user before it is changed. This rule adds no other duty.
  3. **Atomic File Write Integrity** *[Agent + Maintainer]*: Code in the repository that writes a file a later run reads back (ledgers, state, generated files) MUST write it as PRINCIPLE-013 R1 specifies. Edits the agent makes with its own editing tools are outside this rule; R1's commits protect them.
  4. **Non-Breaking Micro-Checkpoints (Test Sanctity Gate)** *[Agent]*: Every commit, milestone commits included, MUST be made on a tree on which every Phase 4 command passed (PRINCIPLE-002 R1), unless the informed override of PRINCIPLE-002 R5 applies. Work that does not pass yet stays uncommitted in the working tree, and the agent describes its state in a `--checkpoint` `--desc` (R5) so that `--resume` reports it; the ledger holds the description, never the code.
  5. **Disruption Ledger, Resumption & Reset Protocol** *[Agent]*: Checkpoints are recorded with `python scripts/disruption_recovery.py --checkpoint <task_id> --phase-num <1-5> --desc <text>` at the moments PRINCIPLE-002 R4 sets. A task is *abandoned* when the user cancels it, or when the agent stops it before `--complete` to work on a different task; the agent MUST then run `python scripts/disruption_recovery.py --reset "<reason>"` before the first checkpoint of the other task. A checkpoint for a different task while one is still in progress records the old task as `superseded` and prints a warning; that warning means this rule was skipped.
  6. **Explicit Staging & Transient Buffer Hygiene** *[Agent]*: Staging follows PRINCIPLE-018 R2. When `--resume` lists dangling `*.tmp_*` files, the agent MUST run `python scripts/disruption_recovery.py --clean` before its first file edit; `--clean` deletes only buffers older than 60 seconds, so a write in progress keeps its buffer.

### PRINCIPLE-007: Pre-flight Impact & Quality Checklist (Cold-Start Gate)
- **Problem**: Rushing into implementation without understanding context, risks, or rationale leads to broken contracts, regressions, or cheapened designs; uncontrolled scope creep leads to speculative over-engineering. When the assessment has no fixed fields and "scope" no definition, one model records a full assessment and another none, and unfinished code ships as done.
- **Concept**: Before the first edit of a Track C task the agent writes into the ledger why the change is needed, what it gains, what it could break in four named ways, and how it guards against each. The task changes only what its plan, its gates or the user require, and the code it leaves contains no unfinished pieces.
- **Invariant**: Track C first plan checkpoint carries --why --benefits --risks (contract, dependency, concurrency, state) --mitigation; no TODO or stub; no change outside the plan.
- **Rules**:
  1. **Adaptive Lifecycle Trigger (Track C Gate)** *[Agent]*: The *impact assessment* is four fields: why, benefits, risks and mitigation. On a Track C task (PRINCIPLE-002 R3) the agent MUST record it before its first file edit, as R6 specifies. Track A and Track B tasks have no impact assessment; a Track B change is verified by Phase 4 (PRINCIPLE-002 R1).
  2. **The 4 Blast-Radius Dimensions** *[Agent]*: The risks field gives one verdict per dimension, each opened by its label: `contract:` (a public contract as PRINCIPLE-004 R4 lists it), `dependency:` (a dependency added or changed, PRINCIPLE-003 R3), `concurrency:` (blocking I/O, locks, threads or processes, PRINCIPLE-010), and `state:` (a persisted file format or schema changed without migration or atomic write, PRINCIPLE-013). A verdict is `none` or the concrete risk, and every concrete risk MUST have an entry in the mitigation field.
  3. **Anti-Satisficing, Type Preservation & Zero Lazy Code** *[Agent + Maintainer]*: Code MUST NOT contain a `TODO`, `FIXME`, `XXX` or `HACK` comment marker; a function whose body is only `pass`, `...` or `raise NotImplementedError`, unless it is abstract, an overload, or declared in a Protocol or ABC; or a `# type: ignore` or `# noqa` that names no error code. `python scripts/update_knowledge_base.py` fails on each of them. The other forbidden shortcuts have their own owners: swallowed exceptions PRINCIPLE-003 R6 and PRINCIPLE-000 R5, weakened tests PRINCIPLE-014, and quality trade-offs PRINCIPLE-000 R4.
  4. **Scope Ceiling (Anti-Gold-Plating Invariant)** *[Agent]*: A change is *in scope* when a milestone of the recorded plan needs it, when it fixes a Phase 4 failure met during the task, or when the user asked for it. The agent MUST NOT make an out-of-scope change in the task; it lists each one to the user as a suggestion in its final message.
  5. **Reversibility, Recoil Preparedness & Principle 8 Bridge** *[Agent]*: Before the first file edit of a Track C task, when `git status --short` lists files the task did not change, the agent reports them to the user (PRINCIPLE-004 R2) and never stages them (PRINCIPLE-018 R2). The commit before the task is its rollback point, reached only by PRINCIPLE-018 R5's non-destructive recoil. Every mitigation that needs code MUST be part of a plan milestone (PRINCIPLE-008).
  6. **Persistent Assessment Memory & Conversational Conciseness** *[Agent]*: The assessment is recorded on the task's first plan checkpoint: `python scripts/disruption_recovery.py --checkpoint <task_id> --phase-num 2 --desc "[1/M] ..." --why <text> --benefits <text> --risks "contract: ...; dependency: ...; concurrency: ...; state: ..." --mitigation <text>`. The command exits 2 while a field or a risk verdict is missing; later plan revisions need not repeat it. In the conversation the agent states the assessment in at most 4 lines, one per field.

### PRINCIPLE-008: Hierarchical Problem & Task Decomposition
- **Problem**: A task done as one monolithic change leaves broken intermediate code and imports of symbols that do not exist yet; a task cut into dozens of tiny steps creates churn; delegated work without bounds exhausts context. When the size limits, the unit of a milestone and the re-plan step are not defined, each model decomposes differently, and sub-agents that write the shared ledger corrupt the parent task's state.
- **Concept**: A Track C plan has at most six milestones, ordered so that nothing is used before it is built, each passing the gates on its own. A changed plan is recorded as a new plan, delegated work is bounded, and only the parent task writes the ledger.
- **Invariant**: Plan of M<=6 milestones (more: split into tasks), built bottom-up, each passing Phase 4 alone; re-plan = new `[1/M']` checkpoint; sub-agents never write the ledger.
- **Rules**:
  1. **Dual-Pillar Framework** *[Agent]*: *Pillar A*: a Track C task is decomposed as Goal, then the PRINCIPLE-009 layers it touches, then milestones. *Pillar B*: work the agent delegates is bounded: the agent the user talks to is level 0 and a sub-agent is one level below the agent that started it; no sub-agent MAY run at a level deeper than 3, and one sub-agent MUST NOT receive more than 50 files or records in one brief.
  2. **Top-Down Decomposition, Bottom-Up Execution** *[Agent]*: The plan is written goal first and executed foundations first: no milestone may use a class, function, flag or file that a later milestone creates (PRINCIPLE-003 R1).
  3. **Bounded Milestone Horizon & Indexing Contract** *[Agent]*: A plan has 1 to 6 milestones. When the decomposition yields more than 6, the agent MUST split the work into separate tasks, each with its own task ID and plan, and tell the user the order of the tasks. Milestones are numbered N = 1..M in the plan (PRINCIPLE-004 R1) and committed as PRINCIPLE-006 R1 specifies.
  4. **Single-Domain Leaf Atomicity & Independent Verifiability** *[Agent]*: A milestone changes one PRINCIPLE-009 layer together with its tests and documentation; when it must change more than one layer, its plan entry states why; and its commit MUST pass Phase 4 on its own (PRINCIPLE-006 R4).
  5. **Dynamic Re-Decomposition on Discovery** *[Agent]*: When the agent finds that the recorded plan cannot be completed as written, it MUST record the revised plan as a new `[1/M']` Phase 2 checkpoint (PRINCIPLE-004 R1) before its next file edit. Committed milestones keep their numbers; later commits use M'. When M' would exceed 6, the milestones after the current one become a separate task with its own plan (R3).
  6. **State & Context Propagation** *[Agent]*: A sub-agent receives in its brief the milestone it serves, the files it may change and the commands that verify its result. It MUST NOT write `.agents/task_ledger.json`; it returns its result to the parent, and only the parent records checkpoints, so one task has one ledger writer.

## 🏗️ Phase 3: Architecture & Lean Implementation

### PRINCIPLE-009: Modularity & Pluggable Architecture
- **Problem**: Monolithic code, hardcoded infrastructure, multi-directory boilerplate on small scripts and catch-all `utils.py` modules couple business logic to frameworks, making systems brittle and untestable. When the rules do not say which code they cover, one model demands four layers in a 200-line script and another ignores them in a multi-backend service.
- **Concept**: Three structural rules hold for every module and are checked by a gate. Layering, registries, constructor injection and immutable data objects apply where a role has two or more implementations, the place where coupling does damage.
- **Invariant**: Every module: no junk-drawer name, roles of 1-5 methods, no import cycle (gated). At a pluggable boundary: 4 layers, registry lookup, constructor DI with default, frozen DTOs.
- **Rules**:
  1. **Canonical 4-Layer Architecture & Scalable Layering** *[Agent]*: A *pluggable boundary* is a role with two or more production implementations in the repository or in the recorded plan, such as storage backends or providers; a test double alone does not make one, though it is still injected as R4 specifies. Code at a pluggable boundary MUST separate four layers: Presentation (parses input and renders output; holds no business rule, query or file I/O), Service (orchestrates use cases), Domain (entities and rules; imports no framework, database or UI module) and Adapter (implements a role for one backend). The layers MAY share one module of at most 300 lines; above that, each layer is its own module. No module, at a boundary or not, MAY be named `utils`, `util`, `helpers`, `helper`, `common` or `misc`.
  2. **Interface Segregation & Narrow Role Protocols (Anti-Fat-Interface)** *[Agent]*: A role is declared as a `typing.Protocol` or `abc.ABC` with 1 to 5 methods, or, when it has exactly one operation, as a `Callable` type; every implementation implements all of its methods; a stub implementation is rejected by PRINCIPLE-007 R3.
  3. **Pluggable Registry & Open-Closed Extensibility (OCP)** *[Agent]*: Service code MUST select among a role's implementations by looking a name up in a dictionary or registry, never by an `if`/`elif` chain on the name, so adding an implementation changes no service code.
  4. **Pure-Stdlib Dependency Injection & Zero-Config Usability** *[Agent]*: A service that uses a role MUST receive it as a constructor parameter that defaults to `None` and falls back to the default implementation (`self._adapter = adapter or DefaultAdapter()`), so the service runs with no configuration (PRINCIPLE-011) and a test injects a double (PRINCIPLE-014). A third-party DI container is a dependency under PRINCIPLE-003 R3.
  5. **Unidirectional Flow & Immutable Data Transfer Objects (DTOs)** *[Agent]*: Presentation imports Service, Service imports Domain, Adapter imports Domain, and no module imports, directly or through others, a module that imports it. Data passed between layers is a `dataclass(frozen=True)` or a `NamedTuple`. Code MUST NOT assign to another module's or object's `_private` attribute. `python scripts/update_knowledge_base.py` fails on a junk-drawer module name, a role outside 1 to 5 methods and an import cycle.

### PRINCIPLE-010: Performance & Resource Optimization (Speed & Lean Architecture)
- **Problem**: Quadratic loops, blocking I/O on event loops, hung subprocesses, disk thrashing from per-record `fsync`, daemon memory creep, heavy startup imports and slow test suites degrade performance and developer velocity. When a limit is stated twice with different numbers, or as "heavy" or "unbounded", each model applies a different one.
- **Concept**: Each performance limit is one number, stated once and measured by a test or a gate; the decidable resource rules are checked in every module.
- **Invariant**: Stream uncontrolled input; threads only for steps >=200ms; timeout= on subprocess, with on open(); one fsync per file; `--help` <200ms; unit <1s, integ <5s.
- **Rules**:
  1. **Algorithmic Stream Processing ($O(1)$ Auxiliary Memory)** *[Agent]*: A membership test inside a loop MUST use a `set` or `dict`, never a `list` or `tuple` that grows with the input. Input whose size the program does not control (user data, logs, network or process streams) MUST be read incrementally (iteration, `yield`, bounded chunks), never whole. Files the tool itself writes and bounds, such as its sources, rule files and the 20-entry ledger, MAY be read whole.
  2. **Non-Blocking Event Loops & Measurement-Driven Concurrency** *[Agent]*: Inside `async` code or a GUI main thread, file, process, database and network calls MUST run through `asyncio.to_thread()` or a worker thread. Threads or processes MAY be added to a step only when that step, measured single-threaded, takes 200ms or more; the measurement is stated in the commit message or ADR.
  3. **Subprocess Timeout Gate & Bounded Concurrency** *[Agent + Maintainer]*: Every `subprocess.run`, `call`, `check_call` and `check_output` passes `timeout=`, and every `Popen` is waited on with a timeout. Parallel processes are started through a pool of at most `os.cpu_count()` workers.
  4. **Deterministic Resource Reclamation & Daemon Ring Buffers (RAII)** *[Agent + Maintainer]*: `open()` and `Path.open()` run only as a `with` item; a raw descriptor from `os.open` is closed in `try`/`finally`; other OS resources (sockets, handles, processes) are released in a `with` or `try`/`finally`. A process that runs until stopped keeps every growing collection bounded (`collections.deque(maxlen=N)`, a capped cache). `python scripts/update_knowledge_base.py` fails on a blocking subprocess call without `timeout=` and on `open()` outside a `with`.
  5. **Batch I/O Coalescing & Cold Startup Budget** *[Agent + Maintainer]*: Code that writes many records to one file writes them all and then calls `os.fsync` once; one fsync per file written is PRINCIPLE-013 R1, not a violation. Every CLI answers `--help` in under 200ms as a fresh process, interpreter start included, importing only standard-library modules at top level and anything else after argument dispatch; `python scripts/dogfood.py` measures it.
  6. **Sub-Second Unit Test Gate (<1s) & Budgeted Integration Tier** *[Agent + Maintainer]*: `python -m unittest tests.test_kit` finishes in under 1 second and spawns no process and calls no `time.sleep`; `python -m unittest tests.test_integration` finishes in under 5 seconds with a timeout on every spawn (PRINCIPLE-014). A test that spawns processes is moved to the integration tier, never deleted to protect the unit number. Every time limit in this principle is measured on the machine that runs Phase 4, and a breach there is fixed before the commit.
  7. **Clean Optimization (Anti-Cleverness Invariant)** *[Agent]*: An optimization that makes code harder to read (manual caching, inlining, bit tricks, precomputed tables) MUST state its before and after measurement in the commit message or ADR; without one, the agent writes the plain version.

### PRINCIPLE-011: Zero-Friction Onboarding & Instant Usability (One-Click Start)
- **Problem**: Setup friction, crashes on a missing environment variable, missing directories, silently simulated success, interactive prompts that hang automated runs, and raw tracebacks block users and agents on their first run. When one rule demands optional dependencies and another allows declared ones, or a demo is only recommended, each model builds a different first-run experience.
- **Concept**: A clone runs with only its declared dependencies, creates what it needs, never waits for a keyboard unless asked to, says when it falls back, exits with a fixed code, and explains every failure in three parts.
- **Invariant**: Only declared deps; creates its dirs; prompts only with `--interactive`; no `os.environ[...]` reads; exit 0/1/2; errors give `Why:`/`Fix:`; demo <10s.
- **Rules**:
  1. **Pure-Stdlib Clone-and-Run Baseline** *[Agent + Maintainer]*: After `git clone`, the test command and every CLI MUST run with only the dependencies declared under PRINCIPLE-003 R3; AIKit declares Python 3.10+ and `git`. A dependency that only one adapter uses is imported inside that adapter, so every other module runs without it (PRINCIPLE-009).
  2. **Self-Bootstrapping Workspace & Zero-Prompt Auto-Init** *[Agent]*: A program creates each directory it writes into (`mkdir(parents=True, exist_ok=True)`) and uses a documented default for each missing setting (PRINCIPLE-003 R6). It MUST NOT read the keyboard (`input()`, a confirmation prompt) unless the user passed `--interactive` or `-i`.
  3. **Zero-Crash Config Protocol & Explicit Mode Transparency** *[Agent + Maintainer]*: Code reads environment variables with `os.getenv()` and a default, never `os.environ[...]`; `python scripts/update_knowledge_base.py` fails on such a read. When a program runs on a fallback (offline, mock, default configuration) it prints one line naming that mode before its output. An operation that needs a missing credential exits 1 with R6's message and MUST NOT report simulated success.
  4. **Cross-Platform Polyglot Command & Path Parity** *[Agent]*: Paths, subprocess calls and documented commands follow PRINCIPLE-003 R4. A documented command MUST NOT need a shell builtin of one platform (`export`, `set`, `./script.sh`).
  5. **Non-Interactive Headless Parity & Deterministic Exit Codes** *[Agent + Maintainer]*: A command with stdin closed or not a terminal (`not sys.stdin.isatty()`) MUST finish without waiting for input. Every CLI exits `0` on success, `1` on operational failure and `2` on a usage error (unknown flag, missing or invalid value).
  6. **Actionable Remediation Triad (Anti-Cryptic Error Invariant)** *[Agent + Maintainer]*: A failure message printed to a user, on stdout or stderr, has three parts: a first line stating what failed, a line whose first non-blank text is `Why:` with the cause, and one whose first non-blank text is `Fix:` with the exact command or step that resolves it. A usage error (exit `2`) prints its message on stderr. A CLI MUST NOT let an exception's traceback reach the user.
  7. **Idempotent Health Diagnostics & Self-Demonstrating Fixtures** *[Maintainer]*: The project MUST have a read-only command that reports its runtime and workspace state, and one command that exercises its main use end to end, without external data, in under 10 seconds. In AIKit these are `python scripts/disruption_recovery.py --audit` and `python scripts/dogfood.py`.

### PRINCIPLE-012: Token Frugality & Lean Code Architecture (Context Budgeting)
- **Problem**: Unbounded payload dumps, prompt-cache misses, tool output explosions, runaway agent loops and ceremonial boilerplate exhaust context windows and inflate LLM costs. When one principle governs both the agent's own output and the code that calls an LLM without saying which rule binds which, and states limits as targets, each model applies a different subset.
- **Concept**: Rules R1, R2, R4, R6 bind code that calls an LLM API; R3, R5 and R7 bind the agent and the code it writes. Each limit is one number or one structure that a reader of the code or the transcript can check.
- **Invariant**: LLM code: <=16k-char payloads, static prefix first, schema-checked replies, 429 backoff, step caps; agent: diff -U3, search <=50 hits, relative paths.
- **Rules**:
  1. **Bounded Prompt Payload Ceilings & AST Slicing** *[Agent + Maintainer]*: Code that sends a prompt to an LLM MUST keep the variable tail of one request (R2) at or below 16,000 characters in total, building it from `knowledge/codebase_map.md` entries, summaries or line slices (PRINCIPLE-004 R3), never from whole files concatenated.
  2. **Prompt Cache Alignment & Deterministic Prefix Partitioning (Cache-Friendly Invariant)** *[Agent + Maintainer]*: Such code MUST order each request as a static prefix (system instructions, rules, tool definitions, output schemas) followed by the variable tail (timestamps, ledger state, user input), and the prefix MUST be byte-identical across requests: no timestamp, session ID or task state in it.
  3. **Tool Output Frugality & Bounded Diff Slicing (Anti-Mega-Log Invariant)** *[Agent]*: A diff the agent puts into the conversation shows at most 3 lines of context per hunk (`git diff -U3` or less); a search shows at most 50 matches (`| head -n 50`, `git grep ... | head -n 50`); a test run shows its summary lines. These limits apply together with PRINCIPLE-004 R5's 100 lines per command, so a search with context lines stops at whichever limit it reaches first.
  4. **Output Token Frugality & Schema-Constrained Generation** *[Agent + Maintainer]*: Code that asks an LLM for data a program consumes MUST request it against a declared schema (JSON Schema or a dataclass) and validate the reply before use, failing with PRINCIPLE-011 R6's message on a mismatch. The agent's messages are limited to 15 lines by PRINCIPLE-004 R5, which owns that number.
  5. **Compact Schema & Relative-Path Serialization** *[Agent]*: Prompts, tool inputs and every persisted file, the ledger included, store repository-relative paths (`scripts/disruption_recovery.py`), never absolute ones; a path outside the repository is the one exception. The ledger converts absolute paths inside the repository itself (`repo_relative`).
  6. **Token-Aware Rate Pacing & Runaway Circuit Breakers (Anti-Death-Spiral Invariant)** *[Agent + Maintainer]*: Code that calls an LLM API MUST retry an HTTP 429 or 529 with exponential backoff and full jitter. Code that runs an autonomous loop MUST define a maximum step count and a maximum token count as named parameters; on reaching either it records a checkpoint (PRINCIPLE-006 R5) and stops for the user.
  7. **Lean Syntactic Density & Anti-Premature-Abstraction (Codebase Token Hygiene)** *[Agent]*: The agent MUST NOT add a function whose body only calls another function with the same arguments, a class holding only one method besides `__init__`, or an abstract base class with one implementation and no plan entry for a second (PRINCIPLE-009 R1). Standard-library primitives (`dataclasses`, `pathlib`, `itertools`, `collections`) come before hand-written equivalents.

## 🛡️ Phase 4: Operational Verification & Resilience

### PRINCIPLE-013: Crash Resilience, State Atomicity & Power-Loss Recovery (Fail-Safe Operations)
- **Problem**: Power cuts, process crashes, Windows lock contention (`WinError 32`), a full disk (`ENOSPC`), schema changes and signals can corrupt state files or leave them half-written. When the rules do not say which files they cover and give ranges instead of numbers, one model retries every write and another none.
- **Concept**: A *state file* is a file the program writes and a later run reads back that no command can rebuild from tracked sources: the ledger, configuration, caches, user data. A *generated file* is rebuilt by a command from tracked sources: the Tier 1 files, the codebase map. State files get the full protection below; generated files are written atomically and repaired by rerunning their generator.
- **Invariant**: State files: >=10MB free, temp + fsync + os.replace (5 tries) + dir fsync, .bak, advisory locking 3s/30s stale, corrupt -> quarantine/.bak/migrate. Generated: temp + fsync + replace.
- **Rules**:
  1. **Atomic Persistence & Lock-Contention Retry Loop** *[Agent + Maintainer]*: A state file MUST be written to a temporary file in the same directory, flushed and `os.fsync`ed, moved into place with `os.replace` retried up to 5 times with exponential backoff on `PermissionError`, and followed by an fsync of its directory. A generated file is written the same way without the retry. No code truncates and rewrites a state or generated file in place.
  2. **Storage Headroom Pre-Flight Check (ENOSPC Resilience)** *[Agent + Maintainer]*: Before writing a state file, code MUST check with `shutil.disk_usage` that at least 10MB are free; below that it writes nothing and exits 1 with PRINCIPLE-011 R6's message.
  3. **Inter-Process Advisory Locking (Anti-Race Invariant)** *[Agent + Maintainer]*: Every read-modify-write of a state file holds an advisory lock file (`<file>.lock`) acquired with a 3-second timeout; a lock older than 30 seconds is broken by an atomic rename, and a timeout raises an error with the triad, never a write without the lock.
  4. **Dual-Slot Shadow Snapshots & Schema Migration (`.bak` Fallback)** *[Agent + Maintainer]*: Before replacing a state file, code copies the current one to `<file>.bak`. On load, a file that does not parse is renamed to `<file>.corrupt_<epoch>`, the `.bak` is loaded instead, and the result passes through the schema migration (`migrate_ledger_schema` for the ledger) before an empty default is used. Each of these steps that fails prints a warning naming the file.
  5. **Signal-Aware Memory Drain & Read-Only Fallback** *[Agent + Maintainer]*: A *long-running* process runs until stopped (a daemon, watcher, server or open-ended loop). It MUST handle `SIGINT` and `SIGTERM` by writing its in-memory state and releasing its locks before exiting. When a state file cannot be written because the filesystem is read-only, the program continues with in-memory state and prints one warning naming the file.
  6. **Multi-File Staging, WAL & Orphan Sanitation** *[Agent + Maintainer]*: Code that writes several files as one change computes every file's content, and runs every check that could refuse the change, before replacing the first file. Temporary buffers left by an interrupted write are removed by `--clean` as PRINCIPLE-006 R6 specifies, never by an automatic sweep at startup.
  7. **Continuous Chaos & Fault-Injection Verification** *[Maintainer]*: The test suite MUST contain at least one test for each fault: a 0-byte state file, malformed JSON, insufficient disk space, recovery from `.bak`, and concurrent writers. Each asserts that the program recovers or fails with PRINCIPLE-011 R6's message, never with a traceback.

### PRINCIPLE-014: Automated Test Verification & Continuous Test Coverage (Regression Shield)
- **Problem**: Changes without tests break contracts; agents weaken or delete failing assertions to pass gates; shared state makes tests order-dependent; tests that only echo mocks prove nothing; leaked files pollute the tree. When "weaken" is undefined and two principles name different exceptions for changing a test, each model decides alone when a test may change.
- **Concept**: Every behaviour change arrives with a test that fails without it; a test changes only to become stricter, or with the user's approval recorded in an ADR; tests run fast, isolated and deterministic; and every safety mechanism is shown to be used, not only to work.
- **Invariant**: 100% test pass gate; behaviour change = failing-first test; weakening a test needs user approval + ADR naming it; unit <1s, no spawns/sleeps; integration <5s; tempdir + addCleanup; reachability shield (`scripts/check_reachability.py`).
- **Rules**:
  1. **Test-Backed Changes & Regression Shield** *[Agent]*: A change that alters observable behaviour (a return value, output, written file, exit code or raised exception) MUST add or change a test in `tests/` that fails on the code before the change and passes after it. A change that keeps behaviour, such as a refactor or a comment, needs no new test; every existing test MUST pass unchanged.
  2. **Test Sanctity Invariant (Anti-Regression Masking)** *[Agent]*: *Weakening* a test is any change after which it accepts a behaviour it rejected before: deleting or skipping it, removing or loosening an assertion, widening an allowlist or threshold. Rewording a test so that it rejects the same behaviours, or more, is not weakening. When a test fails, the agent fixes the code. It MAY weaken a test only when the user approved the contract change the test encodes, and the ADR of that change names the test and the approval (PRINCIPLE-000 R5).
  3. **Two-Tier Test Budget & Zero Flakiness (<1s Unit Gate)** *[Agent + Maintainer]*: `python -m unittest discover tests` runs both tiers. The unit tier (`tests/test_kit.py` in AIKit) finishes in under 1 second, spawns no process and never calls `time.sleep`; the integration tier (`tests/test_integration.py`) holds every test that must spawn a process, finishes in under 5 seconds, and gives every spawn a timeout (PRINCIPLE-010 R6). No test makes a network call; randomness is seeded and time is injected. A test that fails on a rerun of unchanged code is *flaky* and blocks every commit until fixed.
  4. **Pristine Working Tree & RAII Fixture Reversion** *[Agent]*: A test writes files only inside a temporary directory it creates, and restores every global it changes (`os.environ`, `sys.argv`, module attributes, logger levels) with `self.addCleanup` or a context manager. After the suite runs, `git status --porcelain` shows nothing the suite created.
  5. **Observable Contracts Over Mock Echoes (Anti-Tautological Invariant)** *[Agent]*: Every test asserts at least one observable result: a return value, output, a written file, a state change or a raised exception. A test whose only assertions are on mock calls (`assert_called_once` and the like) or on private attributes does not count as the test R1 requires.
  6. **Red-Green Defect Pinning & Hostile Negative Path Hardening** *[Agent]*: A bug fix starts with a test that reproduces the bug and fails (red), then the fix makes it pass (green). Each new public function or CLI flag gets at least one test with invalid input (empty, `None`, a 0-byte file, a malformed value) that asserts the exact exception or message.
  7. **Invariant Reachability Shield (Anti-Dead-Capability Invariant)** *[Agent + Maintainer]*: A passing test proves a mechanism works, not that it is used. `python scripts/check_reachability.py` fails when a production function has no production call site or entrypoint (a test call does not count), or when production code reads a persisted key no production code writes. When a principle names a mechanism (a lock, a retry, a migration), the agent verifies it is called on the path it protects before reporting the work done.

### PRINCIPLE-015: Universal Operational Dogfooding & Chaos Verification (The AI Must Use What It Builds)
- **Problem**: Unit tests in isolation miss real interaction bugs; dev servers leak zombie processes; prompts hang in subshells; a page can return HTTP 200 and render nothing; GUI windows crash without a display. When the rules do not say whose runner they mean, when it runs, or which of three line limits applies, each model dogfoods differently or not at all.
- **Concept**: The agent runs what it builds the way a user would, in a sandbox, on the golden path and under one hostile input, and the run is a commit gate. AIKit's `scripts/dogfood.py` does this for AIKit's own tools; a project built with AIKit has its own runner for its own product.
- **Invariant**: Domain-specific interactive dogfooding via `scripts/dogfood.py` (or the project's runner) as a commit gate; golden path + chaos perturbation; non-interactive stdin parity; portable RAII process tree teardown; ephemeral safety jail; terse reporting (<=15 lines).
- **Rules**:
  1. **Domain-Specific Interactive Dogfooding & Headless Parity** *[Agent + Maintainer]*: The project's dogfood runner exercises its product the way its users do, by product type. A desktop GUI is opened (offscreen or a virtual display), its controls are used and its window destroyed within 10 seconds, with no unhandled callback exception. A web app is served on a free port, loaded in a headless browser, and its root container (`#root`, `#app`) has rendered children and no `console.error`. A CLI runs as a real process with real arguments and closed stdin, and its exit codes are checked. A backend API is started, called over HTTP, and answers with the declared status, schema, and within 500ms. AIKit's runner is `python scripts/dogfood.py`, for AIKit's CLIs; an adopting project writes its own.
  2. **Platform-Portable Process Tree Teardown (RAII Cleanup)** *[Agent + Maintainer]*: Every process a runner starts runs inside a context manager that, on exit or on a failed assertion, kills the whole process tree: `taskkill /F /T /PID <pid>` on Windows, `os.killpg(pid, signal.SIGKILL)` on POSIX. AIKit's is `supervised` with `terminate_process_tree`.
  3. **Non-Interactive Stdin Parity & EOF Safety** *[Agent + Maintainer]*: The runner starts every command with stdin closed, so a command that waits for input fails the run; the duty itself is PRINCIPLE-011 R2 and R5.
  4. **Hermetic Ephemeral State & Storage Sandboxing** *[Agent + Maintainer]*: Everything a run writes (state files, databases, caches, logs) goes under one temporary sandbox directory created for the run. The runner records a content fingerprint of the repository before and after the run and fails when it changed; it MUST NOT write to the user's home folders.
  5. **Dual-Track Dogfooding (Golden Path + Hostile Chaos Perturbation)** *[Agent + Maintainer]*: Every run executes (1) one end-to-end golden path that creates, changes and reads back the product's main object, and (2) at least one hostile input (an interrupt, an invalid value, malformed JSON or concurrent requests). Running `--help` alone is not a dogfood run.
  6. **Deterministic Domain Exit Contracts** *[Agent + Maintainer]*: A run passes only when every step met its R1 criterion and no traceback appeared on stderr.
  7. **Terse Context Reporting & Pre-Ship Gate** *[Agent + Maintainer]*: The runner prints at most 15 lines and writes everything else to a log file (`.agents/dogfood_last_run.log` in AIKit). It is one of PRINCIPLE-018 R3's commit gates and runs in Phase 4 (PRINCIPLE-002 R1).
  8. **Realistic Live Budgeting & Sanity Guardrails** *[Agent + Maintainer]*: A dogfood run that calls a live paid provider obeys the step and token caps of PRINCIPLE-012 R6.

## 🚀 Phase 5: Living Synchronization & Delivery

### PRINCIPLE-016: AI Knowledge Base & Continuous Synchronization
- **Problem**: Code changed without its documentation causes drift; a stale `codebase_map.md` leads to invented symbols; a schema described in two documents diverges; an edited ADR erases its rationale. When the rules do not say which document a change updates or when an ADR becomes fixed, each model keeps a different knowledge base, or ships template text as if it described the project.
- **Concept**: `knowledge/` describes this repository, never a template. Each kind of change has one document that records it, the codebase map is generated and gated, and an ADR is fixed once committed.
- **Invariant**: Canonical `knowledge/` sync; atomic code-and-doc pairing; monotonic append-only ADR register; strict AST syntax validation; link integrity shield; `scripts/update_knowledge_base.py`.
- **Rules**:
  1. **Canonical Structure & Router Sitemap (`INDEX.md`)** *[Agent + Maintainer]*: `knowledge/` holds `INDEX.md`, `architecture.md`, `services.md`, `data_models.md`, `state_and_ui.md`, `decisions.md` and `codebase_map.md`; `python scripts/update_knowledge_base.py` fails when one is missing. Each describes this repository: a section that does not apply says "Not applicable" and why, never template text. `INDEX.md` lists every document with one line on what it holds.
  2. **Atomic Code-and-Doc Pairing (Anti-Drift Invariant)** *[Agent]*: In the same commit as the change, the agent updates: `architecture.md` when a module, layer or process boundary is added, removed or moved; `services.md` when a service's responsibility or gate changes; `data_models.md` when a persisted or exchanged schema changes; `state_and_ui.md` when state lifecycle or user interaction changes; `decisions.md` for an architectural decision (PRINCIPLE-004 R4). `codebase_map.md` is never edited by hand; R4 regenerates it.
  3. **Monotonic Append-Only ADR Register** *[Agent + Maintainer]*: An ADR MAY be edited until the commit that adds it; after that its text is fixed. A superseding decision is a new ADR that names the one it supersedes. The one exception is a heading ID that `python scripts/update_knowledge_base.py` reports as duplicate or skipped, which is renumbered and recorded in a new ADR. IDs are consecutive; the next ID is read from the register (PRINCIPLE-000 R3).
  4. **Strict AST Syntax Validation & Freshness Gate** *[Agent + Maintainer]*: `python scripts/update_knowledge_base.py` regenerates `codebase_map.md` and fails on a file that does not parse at the minimum Python version (PRINCIPLE-003 R7); `--check` fails while the committed map differs from a fresh one. It runs in Phase 4 (PRINCIPLE-018 R3).
  5. **Modular SSOT Partitioning & Versioned Data Models** *[Agent]*: `data_models.md` is the sole Single Source of Truth for schemas: a schema's fields are written only there, and other documents link to it. A persisted schema has a version key (`version` in the ledger) and a migration function that fills keys missing from older files (PRINCIPLE-013 R4).
  6. **Slice-View Heading Hygiene & Link Integrity Shield** *[Agent + Maintainer]*: `knowledge/` documents use `##` and `###` headings so a section can be found by searching for its heading and read in slices (PRINCIPLE-004 R3). `python scripts/update_knowledge_base.py` fails when a relative link in `INDEX.md` points to a missing file.

### PRINCIPLE-017: Living Principles System & Automated Synchronization (Auto-Sync Governance)
- **Problem**: Rules copied into several tool-specific files drift apart; a principle missing a section is read differently by each model; domain rules that must be pasted into every file are forgotten. When the schema rule does not match what the generator checks, a principle can pass the check and still break the standard.
- **Concept**: `GUIDELINES.md` is the only hand-edited rule file. One generator validates its schema, writes every derived file from it, and fails a check while any derived file is stale.
- **Invariant**: Cross-IDE rule sync (`scripts/sync_principles.py`); context budget check; 5-section schema compliance; freshness test gate; Tier 1B domain rules (<=1,200 chars).
- **Rules**:
  1. **Canonical Schema, Unique IDs & Strict Validation** *[Maintainer]*: Every principle has, in this order, a `### PRINCIPLE-NNN: <Title>` heading, `- **Problem**:`, `- **Concept**:`, `- **Invariant**:` (its capsule) and `- **Rules**:` with numbered rules, each tagged with its audience and written as PRINCIPLE-000 R7 requires. `python scripts/sync_principles.py` exits 1 on a missing section, an empty title or a duplicate ID.
  2. **Automated Cross-IDE Target Synchronization** *[Agent + Maintainer]*: After any change to `GUIDELINES.md` or `.agents/rules/domain.md`, the agent runs `python scripts/sync_principles.py`, which rewrites every Tier 1 target (`AGENTS.md`, `GEMINI.md`, `.agents/rules/principles.md`, `CLAUDE.md`, `.cursorrules`, `.github/copilot-instructions.md`) and README's principle table as generated files (PRINCIPLE-013 R1). It never overwrites a file it did not generate, and decides that for every target before writing any.
  3. **Deterministic Auto-Sync Freshness Gate** *[Agent + Maintainer]*: `python scripts/sync_principles.py --check` exits 1 while any derived file differs from what `GUIDELINES.md` generates; a unit test asserts `sync_all(check_only=True) == 0`. A commit MUST NOT be made while either fails (PRINCIPLE-018 R3).
  4. **Triad Documentation Consistency & Exact Title Parity** *[Maintainer]*: Principle titles exist exactly once, in `GUIDELINES.md`, so title parity holds by construction. `scripts/sync_principles.py` generates the principle table of `README.md`, the triad's public leg, between its `<!-- principles:begin` and `<!-- principles:end -->` markers, and `--check` fails while it is stale. A `README.md` without the markers (an adopter's) is only checked to list every principle ID or none.
  5. **Dynamic Lifecycle Phase Alignment** *[Maintainer]*: A principle belongs to the nearest `## ... Phase N:` heading above it. Principles appear in non-decreasing phase order, and the last one is in Phase 5; `python scripts/sync_principles.py` exits 1 otherwise. A new principle needs no change to the generator, only a heading in the right phase.
  6. **Tier 1B Domain Invariants Injection & Blueprint** *[Maintainer]*: A project's own rules go in `.agents/rules/domain.md`, started from `.agents/rules/domain.md.template`, at most 1,200 characters. `python scripts/sync_principles.py` appends it to every Tier 1 target below the universal capsules; nobody edits a Tier 1 target by hand.

### PRINCIPLE-018: Automatic Git Workflow (Commit & Push)
- **Problem**: Uncommitted work is lost; blind staging sweeps secrets and clutter into commits; diverged remotes tempt force-pushes; destructive resets erase work. When the rules claim a lock that does not exist, list only some blind-staging forms or give one rollback for every case, each model takes different risks with the user's history.
- **Concept**: The agent commits each verified unit of work with a checked message, stages files by name, pushes without force, and undoes mistakes without discarding anything. The gates are enforced by the agent running them, not by a hook.
- **Invariant**: Automatic conventional commits (`--validate-commit`) + adaptive push, unless the user opts out, never forced; explicit staging (zero `git add .`); pre-commit delivery triad (tests, read-only gates, staged diff); non-destructive recoil.
- **Rules**:
  1. **Automatic Conventional Commits** *[Agent]*: When Phase 4 passes for a milestone or a task (PRINCIPLE-006 R1), the agent commits, unless the user said not to commit; then it stops after Phase 4 and reports the uncommitted files. The subject is `type(scope): description` or `type(scope): [milestone N/M] description`, with a type from `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `perf`, `build`, `ci`, and at most 72 characters; `python scripts/disruption_recovery.py --validate-commit "<message>"` MUST pass before the commit.
  2. **Explicit Staging Invariant (Zero Blind Staging)** *[Agent]*: The agent stages files only by name (`git add <file> ...`). It MUST NOT run `git add .`, `git add -A`, `git add --all`, `git add -u` or `git commit -a`.
  3. **Pre-Commit Delivery Triad Gate** *[Agent]*: No hook enforces this; the agent MUST NOT commit until all three hold on the tree being committed: (1) both test tiers pass; (2) every read-only gate passes: `python scripts/sync_principles.py --check`, `python scripts/update_knowledge_base.py --check`, `python scripts/check_reachability.py`, `python scripts/check_secrets.py` and `python scripts/dogfood.py`; (3) `git status --short` shows exactly the files the change intends staged, and nothing else modified. Items (1) and (2) are Phase 4 (PRINCIPLE-002 R1).
  4. **Adaptive Push & Zero Force Push** *[Agent]*: After a commit the agent pushes to the current branch's upstream, unless the user said not to push. With no remote it reports the commit as local only. When the push is rejected because the remote moved, it runs `git pull --rebase` and pushes again; when the rebase stops on a conflict, it runs `git rebase --abort` and asks the user (PRINCIPLE-003 R6). It MUST NOT run `git push --force` or `--force-with-lease` unless the user asked for that push.
  5. **Non-Destructive Recoil Invariant** *[Agent]*: To undo its own commit that is not yet pushed, the agent runs `git reset --soft HEAD^` (the parent commit); to undo a pushed commit, `git revert <hash>`. It MUST NOT run `git reset --hard`, `git clean`, `git checkout -- <file>`, `git restore <file>` or `git stash drop` on changes it did not make in this task.
  6. **Terse Delivery Confirmation** *[Agent]*: The final message names, for every commit made, its short hash (`git rev-parse --short HEAD`), its subject, the number of files and the branch, and says whether it was pushed.

### PRINCIPLE-019: Secret & Sensitive Data Hygiene (Irreversible Disclosure Shield)
- **Problem**: Secret leakage is the only defect class with no clean rollback: once a credential reaches a commit, a log, a prompt payload, or a shared artifact it must be rotated, not reverted, and `git reset` cannot help. AI agents are structurally prone to it — they paste environment contents into diagnostics, commit scaffolding wholesale, and persist free-text rationale to disk where it is committed like any other file.
- **Concept**: Credentials live only in the environment or a secret store. Every surface an agent writes (code, docs, the ledger, logs, prompts) is scanned before it can be committed, and a credential that escaped anyway is rotated, never "removed".
- **Invariant**: Zero credentials in tracked files, logs or ledgers; secrets via env/secret store; `.gitignore` credential baseline; `scripts/check_secrets.py` scans staged diffs + ledger; redacted diagnostics; rotate, never revert.
- **Rules**:
  1. **Zero Credentials in Tracked Files** *[Agent]*: No API key, token, password, private key, certificate, connection string or session cookie is written to a tracked file or a commit message. Code reads secrets from the environment with `os.getenv` (PRINCIPLE-011 R3); a tracked template holds only a named placeholder (`API_KEY=<your-key-here>` in `.env.example`).
  2. **Ignore-List Baseline (Pre-Exposure Shield)** *[Maintainer]*: `.gitignore` MUST contain these patterns before any such file exists: `.env`, `.env.*`, `!.env.example`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `id_rsa*`, `id_ed25519*`, `credentials`, `credentials.*`, `secrets.*`, `*.tfvars`, `.aws/`, `.gcloud/`, `.azure/`. A unit test checks that each is present.
  3. **Agent Working Memory Is Tracked Output** *[Agent]*: Text the agent writes to `.agents/task_ledger.json`, ADRs, logs or progress notes names a secret (`the staging API key`) and MUST NOT contain its value, an authorization header or a raw provider response.
  4. **Redacted Diagnostics & Prompt Payloads** *[Agent + Maintainer]*: Code MUST NOT print, log or send to an LLM the whole environment (`os.environ`), full request headers or a raw authentication response; a message that shows a credential-shaped value shows at most its first 4 characters followed by `***`.
  5. **Mechanical Pre-Commit Secret Scan** *[Agent + Maintainer]*: `python scripts/check_secrets.py` scans the staged diff and agent memory (the ledger and the dogfood log), `--all` scans every tracked file; it exits 1 on a finding or on a surface it could not scan, and it is a PRINCIPLE-018 R3 commit gate. A false positive is allowed only by a `# aikit:allow-secret` comment on that line or an entry in `STRONG_ALLOWLIST` or `WEAK_ALLOWLIST` (`scripts/check_secrets.py`), each added in a commit whose message says why.
  6. **Rotate, Never Revert (Irreversibility Protocol)** *[Agent]*: When a secret may have been exposed, the agent tells the user that it must be rotated or revoked first and the artifact purged second. It MUST NOT present `git reset`, a force-push or a deleted file as the remedy.
  7. **Least-Privilege Defaults & Zero Secret Fabrication** *[Agent]*: A step that only reads uses a read-only credential when the provider offers one. The agent MUST NOT invent, guess or fill in a credential value to make a flow proceed; a missing credential ends with PRINCIPLE-011 R6's message.
